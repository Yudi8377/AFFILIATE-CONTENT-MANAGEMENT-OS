# Quality Gates and Change Control

Status: PLANNED. Apply these gates to every implementation slice.

## Evidence-based delivery

Use explicit states: PLANNED, IN_PROGRESS, IMPLEMENTED, TESTED, LIVE_VERIFIED. Do not promote a state without evidence attached to the relevant commit or release note.

## Change protocol

1. Inspect current files, dependencies, deployment configuration, schema, permissions, and CI before editing.
2. Record the intended behavior, affected surfaces, risks, rollback path, and acceptance tests.
3. Work on a dedicated branch; do not rewrite unrelated modules.
4. Keep each commit small and reversible. Prefer additive migrations and compatibility layers.
5. Run formatting, type checks, unit tests, production build, and relevant integration/smoke tests.
6. Inspect the actual deployed URL and critical user journey before calling a release live.
7. Report failures and unverified steps explicitly.

## Security gates

- No database URL, API key, signing secret, or privileged token in browser code or committed files.
- Enforce authorization server-side or with verified database row-level security; hiding a button is not authorization.
- Every admin action affecting users, roles, licenses, money, publishing, or deletion requires permission checks and audit events.
- Validate all untrusted input; encode rendered content; protect against XSS, CSRF where applicable, injection, IDOR, and open redirects.
- Rate-limit or budget expensive generation actions when a secure enforcement point exists.
- Use safe defaults: public reads only for intentionally published content; private drafts and user data remain private.

## Functional gates

- No decorative-only menus for modules represented as operational.
- Every CRUD workflow must demonstrate create, list, detail, update, delete/archive, validation, loading, empty, and error states as applicable.
- Forms need server/database constraints in addition to client-side checks.
- Test deep links, refresh, responsive layouts, keyboard navigation, and accessible labels.
- Test auth lifecycle including sign-up/invitation, sign-in, refresh, expiration, sign-out, denied role, and direct URL access before enabling protected areas.

## SEO gates

- Unique title and meta description for indexable pages; canonical URL; correct status and robots directives.
- Sitemap includes only canonical, indexable URLs; no private dashboard pages.
- Structured data must match visible page content and schema requirements.
- Avoid thin, duplicated, autogenerated pages; drafts are not indexed.
- Do not fabricate keyword search volume or keyword difficulty. Label third-party estimates as estimates and Search Console data as observed data when available.

## AI and media gates

- Every provider adapter starts UNVERIFIED and cannot be represented as available until a real API smoke test succeeds.
- Verify terms, commercial rights, data handling, quotas, rate limits, and zero-cost assumptions before activation.
- Provider secrets stay server-side. If there is no secure server runtime, remote generation remains disabled.
- Validate generated output against a schema; record provenance; distinguish sourced product facts from generated copy.
- Require review before publication. Never auto-publish unreviewed legal claims, health claims, prices, discounts, or affiliate disclosures.
- For video exports, inspect the actual rendered file duration and streams; do not infer completion from job status alone.

## Release report format

Commit/branch; files changed; tests run and their exact results; deployment target; URL tested; known defects; security review; rollback path; statuses that remain unverified.
